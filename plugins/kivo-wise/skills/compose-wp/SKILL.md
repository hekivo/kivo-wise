# Docker Compose for WordPress projects

Every project command goes through the `bin/` scripts at the project root. This skill says which scripts the contract provides, which lifecycle command applies a change, and how to tell a stopped stack from a broken one.

## When to use

- Running WP-CLI, Acorn, Composer, Node, tests, linters, cache flushes, database import/export or log reads in a project whose runner is `compose` (session context line `runner: compose · wp=bin/wp …`).
- Choosing between `bin/up`, `docker compose up -d`, `docker compose restart`, `docker compose build` and `bin/down` after a change.
- Editing `compose.yaml` or the personal override (`compose.override.yaml`, gitignored).
- Site not loading, certificate warnings on `https://<project>.localhost`, port clashes, `docker` not found, "service is not running", the stack in a cloud agent session or an editor devcontainer.
- Not for: Lando projects (`lando-wp`), production or staging hosts, CI pipelines, generating the environment (wp-kit owns that).

## Inputs required

Placeholders below are filled by the session context from the triage JSON. If a placeholder is still literal, read the field yourself:

| Placeholder | Triage field | Example |
|---|---|---|
| `{{runner.wp}}`, `{{runner.acorn}}`, `{{runner.composer}}`, `{{runner.node}}`, `{{runner.test}}`, `{{runner.lint}}`, `{{runner.cache}}`, `{{runner.logs}}` | `runtime.runners` | `bin/wp`, `bin/wp acorn`, `bin/composer`, `bin/npm`, `bin/test`, `bin/mago`, `bin/flush`, `bin/logs` |
| `{{php_service}}` | `runtime.compose.services.php` | `app` |
| `{{web_service}}` | `runtime.compose.services.web` | `app` (PHP-FPM and nginx share one image) |
| `{{db_service}}` | `runtime.compose.services.database` | `db` |
| `{{cache_service}}` | `runtime.compose.services.cache` | `cache` |
| `{{node_service}}` | `runtime.compose.services.node` | `node` |
| `{{session_kind}}` | `runtime.session.kind` | `local`, `cloud`, `codespaces`, `devcontainer` |

Also needed:

- `runtime.compose.contract` (`{ "name": "kivo-wp", "version": 1 }` or `null`), `runtime.compose.bin` (the scripts that exist) and `runtime.compose.files` (the Compose file and the overrides Compose merges).
- `runtime.session.dockerCli`: `false` means this shell cannot reach Docker at all.
- Host facts: `docker version`, `docker compose version`, `docker context ls`, and where the repository lives (on WSL2, the Linux filesystem, not `/mnt/c`).
- The site URL from `bin/info`. The detector never reads `.env` (it holds secrets), so it does not publish one.
- The user's consent before destructive steps: `bin/down --volumes` (deletes the database volume), `bin/db-import` (replaces the database), `docker system prune`.

## Procedure

1. **Read the stack.** Open `compose.yaml` and, when listed in `runtime.compose.files`, the override; list the services and the `bin/` scripts (`ls bin/`). `bin/` is the only supported entry point: with a known contract the service and script names are wp-kit's (`app`, `db`, `cache`, `node`, `proxy`, `mail`), so trust them instead of guessing from images. Without a contract, use the roles the detector derived from the images and say that the project is not on the kivo-wp contract. Details: [references/compose-file.md](references/compose-file.md), [references/bin-scripts.md](references/bin-scripts.md).
2. **Check state before any `bin/` command.** `docker compose ps` lists running services and their health. Nothing listed means the stack is stopped: on the first run in a checkout use `bin/setup` (idempotent: builds, starts with health checks, installs dependencies, seeds synthetic data); afterwards `bin/up`. Choose the place flag from `{{session_kind}}` as the contract reference states it: `bin/setup --cloud` in a cloud agent session, `bin/setup --ci` in CI, no flag on a developer machine or in a devcontainer. A cloud agent session starts with no running containers, so this step comes first in every such session ([references/devcontainer-and-cloud.md](references/devcontainer-and-cloud.md)).
3. **Run every command from the project root through `bin/`.** The runner paths are relative, so `cd` to the root first (the directory with `compose.yaml`).
   - WP-CLI: `{{runner.wp}} <cmd>`. Acorn: `{{runner.acorn}} <cmd>` (`bin/wp acorn` on the contract).
   - PHP packages: `{{runner.composer}} <cmd>`. Node: `{{runner.node}} <cmd>`, which runs in `{{node_service}}`.
   - Tests, linters, cache: `{{runner.test}}`, `{{runner.lint}}`, `{{runner.cache}}`; without a cache script, `{{runner.wp}} cache flush` and `{{runner.acorn}} optimize:clear`.
   - Anything without a script: `docker compose exec {{php_service}} <cmd>` (add `-T` when stdin is not a terminal). Never run host `wp`, `composer`, `php` or `npm`: the host copy is not the container's.

   The Composer and Node project that owns Acorn is not always the repository root. Paths inside a container start at the mount target of the project in the service that runs the command (read `volumes:` and `working_dir:` in `compose.yaml`; written `<mount>` below):

   | | `sage-theme` | `acorn-mu-plugin` | `radicle-app` |
   |---|---|---|---|
   | Acorn's `composer.json` | theme folder: `{{runner.composer}} --working-dir=<mount>/<theme path>`; the root one (Bedrock) holds WordPress and plugins | plugin folder: `{{runner.composer}} --working-dir=<mount>/<plugin path>`; root `{{runner.composer}}` only installs WordPress and plugins | project root: `{{runner.composer}}` |
   | `package.json` / Vite | theme folder: `{{runner.node}} --prefix <mount>/<theme path> <script>` | plugin folder: `{{runner.node}} --prefix <mount>/<plugin path> <script>` | project root, in `{{node_service}}` |
   | `{{runner.acorn}}` answers | only while the theme is active | always | always |
4. **Apply a change with the right lifecycle command** (Compose verbs only):

   | Change | Command |
   |---|---|
   | `compose.yaml`, the override, an `env_file` or `environment:` value, ports, volumes | `docker compose up -d` (recreates only the services whose configuration changed; data volumes are kept) |
   | `Dockerfile`, build args, PHP extensions baked into the image | `docker compose build <service> && docker compose up -d` |
   | Wedged process, no configuration change (OPcache, a stuck worker) | `docker compose restart <service>` (does not re-read `compose.yaml`) |
   | Stack stopped, nothing changed | `bin/up` |
   | Empty database wanted, database image major version changed | `bin/db-export` first, ask, then `bin/down --volumes` and `bin/setup` (the volume and its data are deleted) |

   Team settings go in `compose.yaml`; personal ones (an extra port, Xdebug mode) in the gitignored override. The hooks deny edits to a gitignored override: propose the change to the user instead.
5. **Database work.** Import with `bin/db-import <file>`, export with `bin/db-export [file]`, and open a client shell with `bin/db`. Inside the stack the database host is the service name `{{db_service}}` (`DB_HOST=db`), never `localhost`. Read `bin/db-import --help` for the formats it accepts and whether it replaces the database; export before importing over data someone needs.
6. **Diagnose.** `{{runner.logs}}` (stdout and stderr of the services); `docker compose logs -f {{web_service}}` for one service; `debug.log` inside the container when `WP_DEBUG_LOG` is on (`docker compose exec {{php_service}} tail -f <mount>/<content dir>/debug.log`); the health column of `docker compose ps` and the `State.Health.Log` entries of `docker inspect <container>` for a check that never passes. Symptom table: [references/failure-modes.md](references/failure-modes.md). TLS and host names: [references/tls-and-hosts.md](references/tls-and-hosts.md). WSL2 specifics: [references/wsl2.md](references/wsl2.md).
7. **Finish.** `bin/down` stops this project's containers and keeps the volumes; other projects are not affected.

## Verification

- `bin/trust-cert` has been run once on this machine, then `curl -I <site URL>` (URL from `bin/info`, for example `https://<project>.localhost`) answers 200 or a redirect without `-k`. Use `curl -kI` only as a diagnostic to separate "site down" from "certificate not trusted": `-k` hides exactly the TLS failure this check is meant to catch.
- `{{runner.wp}} core is-installed && {{runner.wp}} option get siteurl` matches the URL from `bin/info`.
- `{{runner.acorn}} --version` answers on Acorn projects; `{{runner.composer}} --version` answers.
- `docker compose ps` shows every service running and `healthy` where a health check exists.
- `docker compose exec {{cache_service}} valkey-cli ping` (or `redis-cli ping` on a Redis image) returns `PONG`.
- After `docker compose up -d` for a configuration change: `docker compose exec {{php_service}} env` shows the new value (names only when the value is a secret; never paste secret values).

## Failure modes

| Symptom | Cause | Fix |
|---|---|---|
| "port is already allocated" for 443 or 80 | Another stack (or a Lando proxy) holds the port | `bin/setup` picks a free port; read the chosen one from `bin/info`; or stop the other stack |
| `bin/wp`: service "app" is not running | The stack is stopped | `docker compose ps`, then `bin/up` |
| `docker: command not found` in an editor devcontainer | The shell is attached to the app container, not the workspace container | Reopen the project in the workspace container that the generated `devcontainer.json` defines |
| Certificate not trusted in the Windows browser | Caddy's root CA lives in the Linux side | `bin/trust-cert`, then `certutil -addstore -f ROOT` from an elevated Windows prompt; see `references/wsl2.md` |
| Stdio MCP server hangs or prints garbage | A TTY was allocated on a pipe | Use `bin/wp` (it adds `-T` when stdin is not a terminal) or `docker compose exec -T` |
| Image pull or package install fails with a proxy 403 in a cloud agent session | The host is not in the session's network allowlist | Add the host listed in `references/devcontainer-and-cloud.md` to the allowlist |

The full table (ownership, slow I/O, daemon, database health) lives in `references/failure-modes.md`.

## Escalation

- The `bin/` scripts misbehave or a script the contract names is missing: the contract belongs to wp-kit; collect `bin/info`, `docker compose version`, `docker compose ps` and the failing command, then raise it with the wp-kit maintainers. Do not rewrite generated scripts on your own initiative.
- Docker itself misbehaves (daemon, context, disk): `docker context ls`, `docker info`, `docker system df`; ask before any prune.
- A secret is needed (Composer credentials for ACF Pro, an API key): never ask for the value and never put it in a file or an environment variable; in a cloud agent session it is attached by the session proxy, elsewhere the project documents where it comes from.
- Hosting, CI or production parity questions are outside this skill.
