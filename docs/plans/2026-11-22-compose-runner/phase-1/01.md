# Component 01 — Compose detection and runner map

Phase 1, batch A. Depends on: none. Spec: `docs/specs/2026-11-22-kivo-wise-compose-runner-design.md`
S-2 (Detection) and the detector half of S-3 (Runner map). Decisions: D-008, D-009, D-010, D-012, D-013,
D-018. One pull request, `feat(detect): detect the kivo-wp Compose environment and its bin/ runner`.

## Goal

`scripts/detect-roots-project.mjs` recognises a Docker Compose project with wp-kit `bin/` scripts, reports
it as runner `compose` with the `runtime.compose` and `runtime.session` blocks, publishes the Compose
runner map, and applies the `.roots-stack.json` runner flag as an override with two guards. Lando, DDEV
and `none` projects keep their output (only the two new blocks are added).

## Files

- `scripts/detect-roots-project.mjs` — parser rules, Compose branch, session, flag override, runner map,
  `formatText()`.
- `skills/roots-triage/references/triage.schema.json` — runner enum, `compose` and `session` blocks.
- `test/fixtures/projects/<name>/` — nine new fixtures (below).
- `test/detect-roots-project.test.mjs` — new cases.
- `plugins/kivo-wise/` — regenerated by `scripts/build-codex-plugin.mjs` (the schema lives under `skills/`).

## Steps

### 1. YAML subset parser: anchors and aliases (AC-01-6)

1. Test first: add `test/fixtures/projects/compose-anchors` with a `compose.yaml` that has
   `x-env: &env` followed by a block, `<<: *env` inside a service and a scalar `*alias` value, plus
   `x-kivo-wp:` / `contract: 1` and two services with `image` keys. Assert `parseYamlSubset` does not
   throw, the anchored block is read, merge keys and aliases are absent from the result, and the detector
   adds one note per skipped merge key or alias.
2. In `parseYamlSubset` treat a value that is only `&name` as empty (so the indented block below is read),
   and skip `<<: *name` and any value that is only `*name`, returning the skip to the caller so
   `detectCompose` can turn it into a note. Aliases are not resolved. Flow maps stay unsupported
   (they keep coming back as a string); the contract is read from a block map only.
3. `extends`, `include` and `profiles` the parser cannot read: catch the error per file, push it into
   `runtime.compose.parseErrors` and a note, never rethrow.

### 2. Compose files and the contract (AC-01-1, AC-01-2)

1. Add `COMPOSE_FILES` (`compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`) and
   `COMPOSE_OVERRIDE_FILES` (`compose.override.yaml`, `compose.override.yml`,
   `docker-compose.override.yml`). The first existing root file wins; every existing override is merged
   with the existing `deepMerge()` for reading services only. `COMPOSE_FILE` in `opts.env` produces a note
   and is not followed.
2. `detectCompose(root, env, notes, warnings)` returns `null` when no root Compose file exists, otherwise
   the `runtime.compose` object of S-2: `files`, `contract`, `devcontainer`, `services`, `bin`,
   `parseErrors`.
3. Contract: read the top-level `x-kivo-wp` block map and `Number(contract)`. Version 1 is known:
   services `app` (roles `php` and `web`), `db` (`database`), `cache`, `node`, `proxy`, `mail`, and the
   script names of S-1. A higher number produces the note "unknown kivo-wp contract <n>; reading what
   exists" and falls back to the no-contract rules. No `x-kivo-wp` key means `contract: null`.
4. Roles without a contract come from `image` only, with the S-2 mapping (`php`/`serversideup/php` → php;
   `*fpm-nginx*` → php and web; `nginx`/`httpd`/`caddy` → web or proxy; `mysql`/`mariadb` → database;
   `redis`/`valkey` → cache; `node` → node; `mailpit`/`mailhog` → mail). A service with `build` and no
   `image` is matched only when its name is a contract name, otherwise left out with a note.
5. `devcontainer`: the path of `.devcontainer/devcontainer.json` when it exists, else `null`.
6. Fixtures: `compose-bin` (Sage theme, `compose.yaml` with `x-kivo-wp` contract 1, a gitignored
   `compose.override.yaml`, `.devcontainer/devcontainer.json`, executable `bin/_lib.sh` and the `bin/`
   scripts listed in the S-2 example, each sourcing `_lib.sh` from its own directory) and
   `compose-no-contract` (images only, one Dockerfile-built service with a non-contract name). Assert
   `runtime.compose` equals the S-2 example for `compose-bin`, and the image-derived roles plus the
   left-out note for `compose-no-contract`.

Fixture scripts must keep their executable bit in git (`git update-index --chmod=+x`), and the test checks
the bit so a checkout that loses it fails loudly instead of silently reporting no `bin/`.

### 3. The `bin/` signature check (AC-01-1, AC-01-3)

1. `binSignature(file)`: executable, and its first 4 KB source `_lib.sh` from their own directory, or call
   `docker compose`/`docker-compose`, or call another `bin/` script. `runtime.compose.bin` lists the names
   that pass, sorted. Anything else is ignored with a note naming the file.
2. Fixture `composer-bin-dir`: `composer.json` with `config.bin-dir: "bin"` and vendor-style binaries in
   `bin/`, plus a root `compose.yaml`. Assert `bin` is empty, one note per ignored file, and the
   "no bin/ scripts" warning.

### 4. Precedence and warnings (AC-01-3, AC-01-4)

1. Order (D-009, D-010): flag override (step 6), root Compose, Landofile chain, DDEV, `none`. When Compose
   and a Landofile both exist and no flag decides, the runner is `compose`, `runtime.lando` is still
   filled from `parseLando()`, and the warning is
   `Landofile still present; runner compose chosen (set runner in .roots-stack.json to override)`.
2. New warning rows from S-2: root Compose without `bin/` scripts; `bin/` scripts without a root Compose
   file (runner `none`); runner `compose` with `session.dockerCli` false. A Compose file only under
   `.devcontainer/` is not a signal and produces the note
   `.devcontainer/<file>: editor-attached Compose stack; not used as the runner`.
3. Fixtures `compose-no-bin`, `compose-and-lando`, `devcontainer-legacy` (the older template layout:
   `.devcontainer/docker-compose.yml` with services `app`, `web`, `db`, `redis`, no root Compose file).
   Assert runner, warnings and notes for each.

### 5. `runtime.session` (AC-01-7)

1. `detect()` accepts `opts.env` (default `process.env`). `sessionKind(env)` returns the first match of
   `CLAUDE_CODE_REMOTE=true` → `cloud`, `CODESPACES=true` → `codespaces`,
   `KIVO_WP_CONTEXT=devcontainer` or `REMOTE_CONTAINERS=true` → `devcontainer`, else `local`. Export it so
   component 02 can test parity.
2. `dockerCli`: true when a file named `docker` that is executable exists in a directory of
   `opts.env.PATH` (a directory scan; no process is spawned).
3. `runtime.session` is always present; `runtime.compose` is always present and `null` when no root
   Compose file exists.
4. Tests: one case per signal with an injected environment, one with an empty `PATH` (dockerCli false
   and the docker warning on `compose-bin`), and one asserting that no child process module is used by
   the detector (grep test on the source for `child_process`, which the detector does not import today).

### 6. Flag override with two guards (AC-01-5)

1. In `readFlag()` validate `runner` against `lando | compose | ddev | none`; an unknown value is set to
   `null` with `.roots-stack.json: runner "<x>" is not one of lando, compose, ddev, none`.
2. After detection, a valid flag whose environment exists (Compose file, Landofile, `.ddev/config.yaml`;
   `none` always exists) becomes the runner. A flag whose environment is absent keeps the detected runner
   with `.roots-stack.json: runner "<x>" set but no <x> environment found; using <detected>`. The existing
   drift warning (`runner "<x>" differs from the detected <y>`) stays when the two differ.
3. Fixtures `flag-runner-override` (Compose and Lando present, flag `lando` → runner `lando`, drift
   warning) and `flag-runner-missing-env` (Lando only, flag `compose` → runner `lando`, guard warning).
   The existing `flag-override` fixture keeps its output.

### 7. Runner map (AC-01-8)

1. Move the Lando candidate lists (`scripts/detect-roots-project.mjs:636-642`) into `RUNNER_CANDIDATES`
   and use it from the Lando branch unchanged, so Lando output stays byte-identical.
2. Compose branch of `buildRunners()`: apply `pickTool()` to an object keyed by `runtime.compose.bin`
   names and prefix with `bin/`: `wp` → `bin/wp`; `acorn` → `bin/acorn`, else `bin/wp acorn` when an
   Acorn app exists; `composer` → `bin/composer`; `node`, `test`, `lint`, `cache`, `build`, `dev`,
   `login` from `RUNNER_CANDIDATES`; `logs` → `bin/logs`, else `docker compose logs -f <web> <php>` with
   one name when both roles are the same service.
3. Without `bin/` scripts: `wp`, `acorn`, `composer` become `docker compose exec -T <php service> wp …`
   (`… wp acorn`, `… composer`) when a php role exists; every other key is `null`.
4. `formatText()` prints `compose <file> (contract kivo-wp v<n>)`, or `compose <file>` without a contract,
   where it prints the Lando webroot today.
5. Tests: the full runner map for `compose-bin` equals the S-3 "Result for a kivo-wp project" column;
   `compose-no-bin` gives the `docker compose exec -T` forms; a `formatText()` snapshot for both.

### 8. Schema and regression (AC-01-7, AC-01-9)

1. `triage.schema.json`: runner enum `lando | compose | ddev | none`; `runtime.required` adds `compose`
   and `session`; `compose` is `null` or a `$defs/compose` object with `additionalProperties: false`;
   `session` has `kind` (enum `local | cloud | codespaces | devcontainer`) and `dockerCli` (boolean).
2. The test suite validates every fixture output (old and new) against the schema.
3. Regression test: for every pre-existing fixture, `runtime.runner`, `runtime.runners`, `runtime.lando`
   and `warnings` equal the values on `main` (capture them once into the test as expected literals before
   the change).
4. `node --test test/*.test.mjs test/creator/*.test.mjs test/rebuild/*.test.mjs`,
   `node scripts/validate-skills.mjs`, `node scripts/build-codex-plugin.mjs` then `--check`.
