Phase 1, batch C. Depends on: 01 (detection fields and the `compose-bin` fixture), 02 (session context
goldens that this component's new route changes). Spec: S-5 (new Compose skill), S-4 rows for
`roots-router`, `roots-triage`, `roots-status`/`roots-detect` and `AGENTS.md`, S-6 (cloud facts the skill
states), S-7 (router prompts and the Compose eval). Decisions: D-006, D-007, D-011, D-012, D-013, D-014,
D-017, D-020. One pull request, `feat(skills): add compose-wp and route by runner`.

## Goal

A sibling skill `compose-wp` (invoked as `kivo-wise:compose-wp`) answers "how do I run, restart, rebuild,
read logs" for `kivo-wp` projects, the router sends Compose projects to it and Lando projects to an
unchanged `lando-wp`, and the triage documentation describes the new detection output.

## Steps

### 1. Skill body (AC-03-1, AC-03-2)

1. Write `skills/compose-wp/SKILL.md` with the six sections the validator requires (When to use, Inputs
   required, Procedure, Verification, Failure modes, Escalation), a description that starts with
   "Use when" and names the hand-overs (Lando projects → `lando-wp`, tests → `testing-wp`, the Vite dev
   server → `tailwind-vite-assets`, detection → `roots-triage`). Under 500 lines.
2. Inputs: `{{runner.*}}` from the session context; `{{php_service}}`, `{{web_service}}`,
   `{{db_service}}`, `{{cache_service}}`, `{{node_service}}` from `runtime.compose.services`;
   `runtime.session.kind`; host facts (`docker version`, `docker compose version`, `docker context ls`,
   repository on the Linux filesystem). The site URL comes from `bin/info` (the detector never reads
   `.env`, D-006).
3. Procedure, in the S-5 order:
   1. read `compose.yaml` and the override, list services and `bin/` scripts; `bin/` is the only
      supported entry point; with a known contract trust the wp-kit names (D-012);
   2. `docker compose ps`; first run `bin/setup`, later `bin/up`; the place flag (`--cloud`, `--ci`) is
      chosen from `runtime.session.kind` and written as `bin-scripts.md` states for the contract version;
   3. every command from the project root through `bin/` (D-013); a work-directory table per profile
      (Sage theme folder, Acorn mu-plugin folder, Radicle root) with container paths;
   4. lifecycle table: config or env change → `docker compose up -d`; Dockerfile or build args →
      `docker compose build <svc> && docker compose up -d`; wedged process → `docker compose restart <svc>`;
      empty database → `bin/down --volumes` only after `bin/db-export` and the user's confirmation. No
      Lando verbs anywhere in the table;
   5. database through `bin/db-import`, `bin/db-export`, `bin/db`; `DB_HOST` is the service name;
   6. diagnosis through `{{runner.logs}}`, `docker compose logs -f {{web_service}}`, `debug.log` inside the
      container and the health column of `docker compose ps`.
4. A grep test in `scripts/test-validate-skills.mjs` (or the existing skill tests) fails when the
   lifecycle table of `compose-wp` contains `lando`.

### 2. Verification and failure modes (AC-03-3)

1. Verification: `bin/trust-cert`, then `curl -I <site URL>`; `-k` only as a diagnostic, with the reason
   (it hides the TLS failure the check is meant to catch); `bin/wp core is-installed`,
   `bin/wp option get siteurl`, `bin/wp acorn --version`, `bin/composer --version`, cache service ping.
2. `references/failure-modes.md` table with symptom, cause, fix for every S-5 seed row: port 443 or 80
   allocated (read the chosen port from `bin/info`), "service is not running" (`bin/up`), file ownership
   (UID/GID build args), slow I/O on `/mnt/c`, certificate not trusted in the Windows browser, `docker`
   not found (shell is in the app container, not the workspace container), daemon not reachable, database
   health check never passes, stdio MCP broken by a TTY (`-T`), image pull blocked by the allowlist.
   The SKILL.md failure-modes section lists the top rows and links the reference.

### 3. References (AC-03-1, AC-03-4)

1. `compose-file.md`: services, the override, env files, profiles, the `x-kivo-wp` block-map contract and
   why anchors are kept out of it; cite docs.docker.com.
2. `bin-scripts.md`: the wp-kit `kivo-wp` contract version 1 (script names from S-1, `_lib.sh`, `-T` on
   non-TTY stdin, `bin/wp acorn`), and the rule that the contract is owned by wp-kit (D-012).
3. `tls-and-hosts.md`: Caddy `tls internal`, `https://<project>.localhost`, `vite.` and `mail.` hosts,
   `bin/trust-cert`.
4. `wsl2.md`: Linux filesystem, Docker Desktop WSL integration or Engine in the distro, Windows Root
   store import with `certutil` through `\\wsl.localhost\<distro>\…`, Firefox enterprise roots,
   `localhost` forwarding.
5. `devcontainer-and-cloud.md`: "cloud agent sessions" and "editor devcontainers" only (no product
   names); the stack starts per cloud session; the allowlist hosts of S-6 and the proxy-403 failure;
   the ACF Pro credential is attached by the session proxy and never enters files, environment variables
   or the chat; the skill never asks for a token value (D-006); only the repository and synthetic
   fixtures reach these places (D-007); containers.dev cited directly until the kivo-wisdom corpus change
   lands (D-017).

### 4. Routing (AC-03-5, AC-03-6)

1. `keywords.json`: add `compose-wp` with `compose.yaml`, `docker compose`, `devcontainer`, `bin/wp`,
   `codespace`, `kivo-wp`, `compose-wp`. Shared terms (`xdebug`, `db-import`, `db-export`) stay on
   `lando-wp` for the keyword hook, because the hook does not read the runner; the router skill resolves
   them by runner.
2. `routing.json`: a `routes` entry for `compose-wp` ("run wp/composer/node/tests through bin/; up vs
   restart vs rebuild; TLS, logs"); an intent entry with the Compose terms; and in the `roots-router`
   SKILL.md the rule "how to run / restart / logs goes to `lando-wp` when `runtime.runner` is `lando`
   and to `compose-wp` when it is `compose`" (D-011).
3. `decision-tree.md`: a `compose-wp` row next to the `lando-wp` row, and the "a command to run" bullet
   names both skills by runner.
4. Golden `test/hooks/user-prompt-router/compose-runner-route` with an unambiguous Compose prompt (for
   example "bin/wp says the service is not running after I edited compose.yaml"); the Lando goldens stay.
5. Session-start goldens: the skills line gains `compose-wp`; regenerate each expected output and check
   the diff touches only that line (the line is clamped last, so warnings keep their room).
6. `dev/jev-review/prompts.json`: three Compose prompts (`compose-1..3`: restart after a compose.yaml
   change, TLS warning on `<project>.localhost` from a Windows browser, `docker` not found in the editor
   devcontainer) expecting `compose-wp`; the `lando-*` prompts keep `lando-wp`.

### 5. Triage, commands and AGENTS.md (AC-03-7)

1. `roots-triage` SKILL.md: runner enum with `compose`; the `runtime.compose` and `runtime.session`
   fields; the flag is an override with its two guards (D-010); the new warning rows; the `runner: none`
   row wording.
2. `commands/roots-status.md`: for `compose` run `docker compose ps` trimmed to service and status;
   enum line `<lando | compose | ddev | none>`. `commands/roots-detect.md`: flag enum with `compose`.
3. `AGENTS.md` environment rule: "All `wp`, `composer`, `artisan`, `yarn`, `npm` commands run through the
   project runner from the session context (`lando <cmd>`, or `bin/<cmd>` from the project root)". Keep
   the rest of the file unchanged; the Codex copy is regenerated.

### 6. Eval and checks (AC-03-8)

1. `evals/compose-wp/scaffold.sh` copies `test/fixtures/projects/compose-bin` (same pattern as
   `evals/roots-debugging/scaffold.sh`, removing `.kivo-wise`); `prompt.md` asks how to apply a
   `compose.yaml` env change and clear the Acorn cache.
2. Graders: `skill-fired.md` (`compose-wp`), a runner-neutral command grader ("uses the runner's acorn
   command, for example `bin/wp acorn`"; D-020), `no-bare-host-command.md` reused, and a grader that the
   answer does not use Lando verbs.
3. `node scripts/validate-skills.mjs`, `node scripts/test-validate-skills.mjs`,
   `node --test test/*.test.mjs test/creator/*.test.mjs test/rebuild/*.test.mjs`,
   `node scripts/build-codex-plugin.mjs` then `--check`, `node scripts/sync-codex-manifests.mjs --check`.
   `lando-wp` has no diff (D-011).
