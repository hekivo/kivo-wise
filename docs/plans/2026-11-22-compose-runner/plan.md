# Plan — kivo-wise Docker Compose `bin/` runner support

Spec: `docs/specs/2026-11-22-kivo-wise-compose-runner-design.md` (S-1 to S-8, all approved).
Decisions: `docs/specs/decisions.md` (D-001 to D-021). The component graph (ids, dependencies, acceptance
criteria) lives in `.kion/plan.json` and is rendered to `docs/plans/components.md`; this file is the prose.

## How this plan is graduated

Only phase 1 is detailed into components with acceptance criteria and sub-plans. Later phases are an
outline (goal, spec sections, dependencies, open points) and are detailed into components when the
previous phase closes, so they are planned against the code that phase 1 actually shipped.

## Delivery rules

- Every component is one pull request and a complete unit: code, tests, goldens, the regenerated Codex
  mirror and the documentation it needs (D-001; no one-line pull requests).
- The agent may merge its own pull request once every required check is green (D-001, tooling
  repositories only). This planning change is not merged.
- Release is additive and minor (D-018): the runner enum gains `compose` and `runtime` gains two blocks;
  nothing is removed. Versions are bumped by release-please, never by hand.
- Ordering constraint (cross-repository decision): kivo-wise ships the `kivo-wp` runner before wp-kit
  6.0.0. Phase 1 is therefore the runner itself: detection of the `kivo-wp` Compose contract, the runner
  map and the `compose-wp` skill.

## Phase 1 — the `kivo-wp` runner (detailed)

Goal: a project generated by wp-kit with `compose.yaml` and `bin/` scripts is detected as runner
`compose`, every hook prints the right commands for it, and the router sends "how do I run this" to the
new `compose-wp` skill. Lando projects see no change.

| Id | Component | Batch | Depends | Sub-plan |
|---|---|---|---|---|
| 01 | Compose detection and runner map | A | — | `phase-1/01.md` |
| 02 | Compose session context and hook guards | B | 01 | `phase-1/02.md` |
| 03 | compose-wp skill and runner routing | C | 01, 02 | `phase-1/03.md` |

The three run in sequence. 02 needs the detection fields of 01. 03 needs the `compose-bin` fixture of 01
and changes the skills line of the session-start goldens that 02 rewrites, so it rebases on 02 instead of
racing it.

Phase 1 exit: the three pull requests merged with green checks, then the release-please release pull
request for the minor version merged, so wp-kit 6.0.0 can depend on a published kivo-wise.

## Phase 2 — runner-neutral skills and Lando maintenance fixes (outline)

- Goal: every skill and agent reads correctly on both runners, and the Lando fixes of D-019 ship.
- Spec sections: S-4 (skills affected), S-2 (the Lando warning rows), S-8 (Lando fixes).
- Decisions: D-014, D-016, D-017, D-019.
- Depends on: phase 1 (runner map, `compose-wp` as hand-over target).
- Expected scope (to be split into components when phase 1 closes):
  - Lando maintenance (D-019): detector warnings for `config.cache` and `config.extra_php_extensions`,
    the `mysql:8.4` warning that reads the installed recipe file under `opts.landoConfigDir`, the
    `wordpress-recipe.md` caveat and `failure-modes.md` rows, fixtures `lando-config-cache` and
    `lando-mysql-84`.
  - Topic skill preambles in about 16 skills and 4 agents ("Defaults: Lando `lando wp …`; Compose
    `bin/wp …`"), with no new Lando-only content (D-014).
  - Runner-specific content: `roots-debugging` (runner-neutral OPcache restart and logs hand-over),
    `testing-wp` (headed Playwright URL, `bin/e2e`), `tailwind-vite-assets` (Compose HMR through Caddy,
    Codespaces forwarded port, WSL2), `acorn-background` (`REDIS_HOST` from the cache service),
    `wp-abilities-mcp` (`.mcp.json` with `bin/wp` or `docker compose exec -T`).
  - Manifests and README wording and keywords (`docker-compose`, `devcontainer`).
- Open points: whether the Lando maintenance fixes need their own minor release before the skill sweep;
  how many pull requests the preamble sweep becomes (one per skill family is the likely complete unit).

## Phase 3 — cloud sessions, evals and migration (outline)

- Goal: the Compose path is proven in cloud agent sessions, Codespaces and devcontainers, the evals are
  runner-neutral, and teams have a migration guide.
- Spec sections: S-6 (cloud sessions and Codespaces), S-7 (evals), S-8 (migration guide).
- Decisions: D-007, D-015, D-016, D-017, D-020, D-021.
- Depends on: phase 2 (runner-neutral skills are what the eval variants exercise).
- Expected scope:
  - Evals (D-020): runner-neutral graders everywhere, and Compose variants for `roots-debugging`,
    `testing-wp`, `acorn-stack` and `tailwind-vite-assets` that copy the `compose-bin` fixture.
  - Migration guide page (S-8): Lando to `kivo-wp`, database move, env keys, tooling parity, the Docker
    Engine 28+ mount note.
  - Cloud probe runs of `dev/probes/environment-probe.sh` in a cloud session, a Codespace and a
    devcontainer, closing the "cloud probe pending" facts (Q-021, Q-022, Q-026).
  - Hooks in cloud sessions (D-021): make the hook scripts and the detector vendorable by the wp-kit skill
    sync (a stable file list and a settings snippet), coordinated with the wp-kit plan.
  - docs-brain corpus sources for the Docker Compose manual and the devcontainer specification, in a
    separate kivo-wisdom change (D-017).
- Open points: the wp-kit side of D-021 and of the six S-3 requests (contract marker, `-T`,
  `KIVO_WP_CONTEXT`, the Node.js feature, allowlist hosts, `.kivo-wise/` in `.gitignore`) is planned in
  wp-kit; this phase only consumes it. The probe needs a person to open each environment once.

## Cross-repository requests (tracked here, delivered in wp-kit)

The six requests of S-3 go to the wp-kit plan. Phase 1 does not wait for them: without the `x-kivo-wp`
marker the detector falls back to image-based roles, and without `KIVO_WP_CONTEXT` it still detects the
documented cloud and Codespaces signals.
